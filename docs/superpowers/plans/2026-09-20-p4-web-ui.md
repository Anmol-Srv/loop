# Airtribe Control Plane — P4 Web UI Implementation Plan

> **SUPERSEDED, 2026-09-20.** This plan was built and then removed. The owner
> wanted a native Mac app, not a browser UI, and keeping both meant two clients
> to hold against one API. The web surface — `src/routes/web/`, `templates/`,
> `static/`, and the cookie session layer — was deleted. Kept here because the
> reasoning about POST-redirect-GET, scope-truth in the UI, and the incremental
> log cursor carried over into the native app.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A browser view of the control plane — see the board, filter it, approve what agents propose, and watch a run log — served by the same binary as the API.

**Architecture:** Askama templates rendered server-side by Axum, with HTMX for the handful of places that need to update without a full page load. No JavaScript build step, no `node_modules`, no separate deploy. The HTML routes call the same controllers as the API.

**Tech Stack:** Rust 1.96, Axum 0.8, Askama 0.14, HTMX 2 (vendored), plain CSS.

**Spec:** `docs/superpowers/specs/2026-09-18-airtribe-control-plane-design.md`

**Builds on:** P0–P3.

## Decisions taken in this plan

Three choices the spec left open, decided here rather than deferred:

1. **Askama over Maud.** Templates live in `.html` files, so the markup reads as
   markup. Askama checks them at compile time, so a renamed field breaks the
   build rather than the page.
2. **HTMX vendored, not from a CDN.** One 47 KB file in `static/`. The UI works
   offline, and nothing third-party executes in a page that shows internal work.
3. **Token-paste login, not Google SSO.** SSO is still deferred. A login page
   accepts a token, validates it, and stores it in an httpOnly, SameSite=Strict
   cookie. When SSO arrives it replaces exactly one handler — the rest of the UI
   authenticates through the cookie either way.

## Global Constraints

- All prior constraints hold. Postgres on port **5433**.
- HTML routes reuse the existing controllers. No business logic in a template or
  a handler.
- The cookie is `httpOnly`, `SameSite=Strict`, and `Secure` whenever the request
  arrived over HTTPS.
- Every mutating form posts and then redirects (POST-redirect-GET), so a refresh
  never replays an approval.
- The UI shows the same scope truth as the API: a reader sees no approve
  buttons, because the handler omits them, not because CSS hides them.

**Interfaces:**
- Produces:
  - `acp_server::middleware::session::WebCaller(pub Caller)` — a `FromRequestParts` extractor reading the `acp_session` cookie instead of the `Authorization` header. On failure it redirects to `/login` rather than returning 401, because a browser needs a page, not a status code.
  - `GET /login`, `POST /login`, `POST /logout`
  - `GET /static/{file}` serving the two vendored assets.

`WebCaller` and `Caller` must resolve a token identically — one shared function,
two ways of finding the raw string. A divergence here is a security bug.

- [ ] **Step 1: Write the failing test**

`tests/web_auth.rs`:

1. `GET /` without a cookie returns 303 to `/login`.
2. `POST /login` with a valid token sets an `acp_session` cookie marked `HttpOnly` and `SameSite=Strict`, and redirects to `/`.
3. `POST /login` with a garbage token re-renders the login page with an error and sets no cookie.
4. `POST /logout` clears the cookie.
5. A revoked token's cookie no longer authenticates — revoke it in the database mid-session and confirm the next request redirects to `/login`.

Case 5 is the one worth writing first: it proves the cookie is a pointer to a
token, not a copy of its authority.

### Task 2: The board

**Files:**
- Create: `src/routes/web/board.rs`
- Create: `templates/board.html`, `templates/project.html`, `templates/_task_row.html`
- Modify: `src/routes/web/mod.rs`, `src/app.rs`
- Test: `tests/web_board.rs`

**Interfaces:**
- Produces:
  - `GET /` — every project with its phase progress.
  - `GET /projects/{id}` — phases in order, each with its tasks.
  - `GET /projects/{id}/tasks` — the task list fragment only, for HTMX filter updates.

The filter bar posts to the fragment endpoint with `hx-get` and
`hx-target="#task-list"`, so changing a filter swaps the list without reloading
the page. The same handler serves both the full page and the fragment; a
`HX-Request` header decides which template renders.

Phase progress is `done / total` tasks, computed in one grouped query rather
than per phase. With five projects that difference does not matter; the habit
does.

2. `GET /projects/{id}` renders both phase names in position order.
3. `GET /projects/{id}/tasks?status=done` with an `HX-Request` header returns a fragment with no `<html>` element.
4. A task assigned to an agent renders with a visible agent marker, so a human scanning the board can tell what is delegated.

### Task 3: The approval inbox

**Files:**
- Create: `src/routes/web/inbox.rs`
- Create: `templates/inbox.html`, `templates/_change_card.html`
- Modify: `src/routes/web/mod.rs`, `src/app.rs`
- Test: `tests/web_inbox.rs`

**Interfaces:**
- Produces:
  - `GET /inbox` — pending changes, newest first.
  - `POST /inbox/{id}/approve`, `POST /inbox/{id}/reject` — both redirect back to `/inbox`.

This is the screen the whole design exists to make possible, so it has to show
enough to decide without leaving the page: who proposed it, on whose behalf,
what it would do in plain language, and against which task.

Render the patch as a sentence, not raw JSON. `{"status":"in_review"}` against a
task reads as *move "wire MCP auth" to in_review*. Write a small
`describe(change) -> String` for this and unit-test it over all seven operation
shapes — it is the only place in the codebase that turns data into prose, and it
is worth keeping honest.

A caller without the `write` scope sees the list without buttons, and the POST
handlers reject them regardless.

- [ ] **Step 1: Write the failing test**

1. A pending change appears with its describing sentence.
2. Approving from the inbox applies it and the change leaves the list.
3. Rejecting leaves the target unchanged and the change leaves the list.
4. A `read`-only session sees the list and no approve button, and a forged POST from that session gets 403.
5. `describe` covers all seven operations — table-driven unit test.

### Task 4: Task detail and the live run log

**Files:**
- Create: `src/routes/web/task.rs`
- Create: `templates/task.html`, `templates/_run_log.html`
- Modify: `src/routes/web/mod.rs`, `src/app.rs`
- Test: `tests/web_task.rs`

**Interfaces:**
- Produces:
  - `GET /tasks/{id}` — title, body, status, assignee, artifacts, run log, and the task's change history.
  - `GET /tasks/{id}/log?afterSeq=N` — the run-log fragment, polled by HTMX every 2 seconds while the task is `in_progress`.

The poll interval is set in the template with `hx-trigger="every 2s"`, and the
attribute is only emitted when the task is `in_progress`. A finished task must
not keep polling — that is the difference between a live view and a leak.

`afterSeq` makes the poll incremental: the fragment appends rather than
replacing, so a long log does not re-transfer on every tick.

2. `GET /tasks/{id}/log?afterSeq=2` returns only lines after seq 2.
3. An `in_progress` task's page contains `hx-trigger`; a `done` task's page does not.

## Out of scope, on purpose

- Real-time push (WebSocket or SSE). A 2-second poll on one screen is enough for
  a team of this size, and it cannot drift out of sync.
- Editing tasks from the UI beyond status and approval. The CLI is better at
  data entry, and two write paths means two sets of validation to keep aligned.
- Mobile layout. It is an internal tool used at a desk.
